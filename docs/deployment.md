## 4. 断网和服务不可达时的行为（A13）

原则：**连不上权威服务就不能改库存**。不做离线写入、不做本地队列、不做"恢复后自动同步"。

| 情况 | 系统行为 [候选] |
| --- | --- |
| 页面加载时连不上服务 | 显示"无法连接库存服务器，现在不能查询或修改库存"，不显示任何缓存的数量 |
| 页面已打开，之后断开 | 顶部红色提示条；所有写操作按钮不可用；页面上已有的数量标注"数据截至 hh:mm，可能已过期"，只读 |
| 提交时连接失败或超时 | 明确提示"未确认是否已保存"。员工重新提交时沿用同一个 operation_id，服务端如果已经执行过，就返回原来的结果，不会再扣一次（T02 第 5 节）。页面不会在后台自动重发 |
| 服务端可达，但数据库不可达 | 服务端对所有写请求返回错误，不接受"先记下来以后再写" |
| 服务恢复 | 员工刷新页面，重新读取最新数量后再操作 |

即便前端按钮失效了，服务端仍然要按 D03 自己拒绝不合规的写入。前端的提示只是方便员工，不是保证。

**应急办法 [待 Q01，需业务同意]**：如果客户要求断网时仍能出货，第一版的做法是**纸本应急单**：员工在纸上记下出货内容，服务恢复后按正常命令逐笔补录，补录时注明"应急补录"和纸本编号。补录可能因为库存已不足而被拒，这时要人工处理。这是业务流程，不是软件同步；如果客户不接受，需要另行设计离线冲突协议并单独验证（D02），不属于第一版。

## 6. 升级流程（A11）

### 6.1 应用升级 [候选]

1. 事先通知使用者停用时间；升级在非工作时间进行。
2. 应用进入维护模式：所有新的写请求返回"系统维护中"。
3. **等进行中的请求全部结束**，再做备份。维护模式只挡住新请求；开启前已经进入事务的请求，仍可能在之后提交。如果这时就备份，这些提交会晚于备份，回退时恢复备份就会把它们丢掉。具体做法 [候选，未运行验证]：
   - 撤销应用数据库用户的连接权限：`REVOKE CONNECT ON DATABASE <库名> FROM <应用用户>;`（如果 PUBLIC 有 CONNECT，也一并撤销）；
   - 断开应用用户的现有连接：`SELECT pg_terminate_backend(pid) FROM pg_stat_activity WHERE usename = '<应用用户>';`，被断开的未提交事务会回滚，客户端按第 4 节提示"未确认是否已保存"，恢复后用同一 operation_id 重试；
   - 确认 `SELECT count(*) FROM pg_stat_activity WHERE usename = '<应用用户>';` 为 0，才进入下一步。升级完成、对账通过后再 `GRANT CONNECT` 恢复。
   也可以只等不断开：反复查询 `pg_stat_activity` 直到应用用户没有 `state <> 'idle'` 的会话，但必须同时撤销 CONNECT，否则等待期间仍可能有新连接进来。
4. 做升级前备份（5.2），并确认备份文件能打开。
5. 部署新版本，执行数据库迁移（迁移用单独的管理用户，不受第 3 步撤销的影响）。[事实] PostgreSQL 支持在事务里执行 DDL，Django 文档写明：在支持 DDL 事务的数据库（包括 PostgreSQL）上，一个迁移里的所有操作默认在一个事务里执行，可以用 `atomic = False` 关闭（[migrations.txt，Django 5.2](https://github.com/django/django/blob/stable/5.2.x/docs/topics/migrations.txt)「Transactions」一节，查阅 2026-09-27，未运行验证）。[候选，推断] 文档说的是"一个迁移"，所以一次升级包含多个迁移时，不能指望它们整体原子；中途失败要按 6.3 恢复备份。
6. 运行 5.3 的对账检查。
7. 通过就恢复应用用户的 CONNECT 并退出维护模式；不通过就执行 6.3。

### 6.2 PostgreSQL 升级 [候选]

- 小版本（例如 18.6 → 18.7）：换镜像或安装包，重启，不需要迁移数据；照样先备份。
- 大版本（例如 18 → 19）：单独计划，用备份导出再导入或 `pg_upgrade`，先在副本上演练，再在 CI 里用新版本跑完整的并发测试（第 7 节）后才能上生产。

### 6.3 升级失败时回退 [候选]

回退方式是**恢复升级前备份并部署旧版本**，不写反向迁移。**前提**是 6.1 第 3 步已经完成：应用用户的连接已撤销、没有进行中的事务之后才做的备份。满足这个前提时，备份之后没有应用写入，恢复它不会丢已提交的数据；如果第 3 步被跳过或没有确认，就不能用这份备份回退，要先人工核对备份之后提交了哪些操作。恢复后运行对账检查，再开放使用。A11 要求模拟"升级中途中断"再恢复，这个测试由 T06 之后的发布任务负责，目前没有运行。

**硬性要求（防止一条测试没跑也显示绿灯）** [候选，未运行验证]：

- 测试步骤必须真正执行 `pytest`，不能用 `|| true`、`continue-on-error` 或条件跳过把它变成可选。
- 收集到 0 条测试时 job 必须失败。pytest 在没有收集到测试时退出码是 5，默认会让步骤失败；工作流不能吞掉这个退出码。
- 并发测试数量少于预期时 job 失败：并发测试统一加 `@pytest.mark.concurrency` 标记；单独运行 `pytest -m concurrency --junitxml=concurrency.xml`，再用脚本读 junit 结果，断言实际执行（不含 skipped）的数量 ≥ `docs/test-commands.md` 里写明的预期数量（初始为 7.3 表中的用例数），并且失败数为 0。新增或删除并发测试时同时改这个数字。
- 被跳过（skip/xfail）的并发测试不计入数量；数据库连不上时测试要失败，不能 skip。

### 7.3 并发与失败测试的写法（A05 A06 A10）[候选]

- 用 pytest-django 的 `transactional_db`（或 `TransactionTestCase`），让每个线程用自己的数据库连接、各自真实提交。普通的"每个测试包在一个事务里"的写法会让多个线程看不到彼此的提交，不能证明加锁。
- 每个线程结束时关闭自己的连接。
- **必须证明两个请求真的在同一时刻争用锁**，只在开始时用 `threading.Barrier` 同步不够：一个错误的实现可能因为 A 已经提交、B 才开始读取，照样得到"一个成功、一个被拒"。做法 [候选]：
  - 在命令实现里留一个测试专用钩子，位置在"锁内重新读取之后、写入之前"。测试让线程 A 停在钩子处（例如等一个 `threading.Event`），此时 A 持有锁、尚未提交。
  - 启动线程 B 执行同样的命令，然后断言 B 确实被阻塞：在另一个连接上查 `pg_stat_activity`，看到 B 的会话 `wait_event_type = 'Lock'`（或在 `pg_locks` 里有 B 的 `granted = false`）；并且 B 在 A 放行前没有返回。
  - 放行 A，A 提交；再断言 B 的完成时间晚于 A 的提交时间，且 B 的结果是在锁内看到 A 的占用后作出的（被拒或按剩余量处理）。
  - 钩子只在测试配置下启用，生产配置里是空操作。
- **反例测试**：准备一个去掉 `FOR UPDATE`（包括 ProductAvailability 行的锁）的实现变体，用同样的测试跑它，测试必须失败（B 没有被阻塞，或者两单都成功）。这个反例证明测试能分辨对错；它作为单独的测试用例保留，期望结果是"检测到缺陷"。
- 每个并发测试在一次运行里重复多次（例如 50 次），降低"碰巧没并发上"导致的假通过。重复次数写进 `docs/test-commands.md`。
- 必须覆盖的用例：

| 用例 | 预期 | 验收 |
| --- | --- | --- |
| 可用 5 件，两个订单同时各占用 4 件：(a) 员工已选货位的分配；(b) **接单时还没选货位**（商品级未分配占用，分散在两个订单行上） | 两种情形都恰好一个成功，另一个被拒；可用 1；(b) 中 B 在 ProductAvailability 行上等锁 | A06 A10（I11） |
| 同一用例在去掉 FOR UPDATE 的实现变体上运行 | 测试检测到缺陷（失败），证明测试有效 | A06 |
| 同一 operation_id 并发提交两次 | 只生效一次，两次返回相同结果 | A05 |
| 同一 operation_id、不同内容 | 拒绝 | A05 |
| 占用后发货 | 实物减少，可用不再减少 | A06 A10 |
| 多行命令中间一行不合规 | 整个命令回滚，没有任何流水 | A06 |
| 移位写完出库流水后人为抛异常 | 出库、入库都没有写入 | A06 |
| 重复取消同一订单行 | 只释放一次 | A10 |
| 直接用 SQL 把余额改成负数 | 被数据库 CHECK 约束拒绝 | A06 |
| 两个事务以相反的顺序涉及同一组余额行 | 不死锁（按固定顺序加锁） | A06 |

- 不允许用 SQLite 或模拟对象代替上述测试。

### 7.5 本地开发 [候选]

开发者可以用 Docker（`postgres:18.6`）或 PostgreSQL 官方 Windows 安装包在本机起数据库，连接串用环境变量传入，不写进仓库。具体步骤由 T06 写进 `docs/test-commands.md`。

## 8. 支持责任（占位）

[事实] 用户主要在周末开发，不能当工作日唯一的故障响应人（PROJECT.md）。上线前以下每一栏都要有人名，**目前都是空的**。

| 职责 | 负责人 | 备注 |
| --- | --- | --- |
| 公司侧负责人（决定停用、切回纸本、联系技术支持） | 待定 | 工作日必须有人 |
| 技术支持（应用和数据库故障） | 用户（周末）；工作日：待定 | 需要约定响应时间 |
| 服务器硬件 / 云账号持有人 | 待定 | 云端形态下账号不应挂在个人名下 [候选] |
| 备份检查与恢复演练 | 待定 | 每月一次，记录结果 |
| 密码和密钥保管 | 待定 | 至少两人知道恢复办法 |
